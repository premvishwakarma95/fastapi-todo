# Project Requirements: Todo API

A todo REST API built stage by stage to learn FastAPI. Each stage adds features to the same project. We finish one stage, understand it, then move to the next.

## Goal

By the end, the API supports registered users who manage their own todos, backed by a database, covered by tests, and ready to deploy.

## Tech stack

- Python 3.12
- FastAPI (`fastapi[standard]`, includes Uvicorn)
- Pydantic for validation
- SQLite with SQLModel or SQLAlchemy (stage 4)
- Alembic for migrations (stage 4)
- JWT auth with password hashing (stage 5)
- pytest and `TestClient` for tests (stage 7)

## Todo data model

| Field | Type | Notes |
|---|---|---|
| `id` | int | Generated by the server |
| `title` | str | Required, 1 to 100 characters |
| `description` | str or null | Optional, up to 500 characters |
| `completed` | bool | Defaults to `false` |
| `priority` | int | 1 (low) to 3 (high), defaults to 1 |
| `due_date` | date or null | Optional |
| `created_at` | datetime | Set by the server |
| `owner_id` | int | Added in stage 5 |

## Endpoints

### Todos

| Method | Path | Purpose | Stage |
|---|---|---|---|
| GET | `/todos` | List todos, with filters | 1 |
| GET | `/todos/{id}` | Get one todo | 1 |
| POST | `/todos` | Create a todo | 1 |
| PUT | `/todos/{id}` | Replace a todo | 1 |
| PATCH | `/todos/{id}` | Update some fields | 2 |
| DELETE | `/todos/{id}` | Delete a todo | 1 |

List filters (query params): `completed`, `priority`, `search` (title contains), `skip` and `limit` (pagination).

### Users and auth (stage 5)

| Method | Path | Purpose |
|---|---|---|
| POST | `/users` | Register |
| POST | `/auth/login` | Log in, returns a JWT |
| GET | `/users/me` | Current user |

## Rules

- Return correct status codes: 200, 201, 204, 404, 422, and 401 or 403 once auth exists.
- A missing todo returns 404 with a clear message.
- Invalid input returns 422 with Pydantic's error details.
- Use separate request and response models. Never return password hashes.
- After stage 5, a user can only see and change their own todos.

## Stages

Each stage has a goal, what to build, and a "done when" check.

### Stage 1: Basics
- **Build:** In-memory todo CRUD using a Python list or dict.
- **Learn:** Path operations, path and query params, request bodies, `/docs`.
- **Done when:** All five CRUD endpoints work from Swagger UI.

### Stage 2: Validation
- **Build:** Pydantic models for create, update and response. Add `PATCH`.
- **Learn:** `Field` constraints, `response_model`, status codes, `HTTPException`.
- **Done when:** Bad input gets a 422 and a missing todo gets a 404.

### Stage 3: Structure
- **Build:** Move code into `app/` with `APIRouter` and dependencies.
- **Learn:** Project layout, `Depends`, shared query params such as pagination.
- **Done when:** `app/main.py` only wires routers together.

### Stage 4: Database
- **Build:** Replace the in-memory store with SQLite. Add migrations.
- **Learn:** DB session as a dependency, models vs schemas, Alembic.
- **Done when:** Todos survive a server restart.

### Stage 5: Auth
- **Build:** Registration, login, JWT, and per-user todos.
- **Learn:** Password hashing, OAuth2 password flow, security dependencies.
- **Done when:** User A cannot read or change user B's todos.

### Stage 6: Async and background
- **Build:** An async version of an endpoint, a background task (for example logging or a fake email on todo creation), and a lifespan handler.
- **Learn:** `async def` vs `def`, `BackgroundTasks`, lifespan events.
- **Done when:** You can explain when to use `async def` and when not to.

### Stage 7: Production
- **Build:** pytest suite, settings from environment variables, CORS, Dockerfile.
- **Learn:** `TestClient`, dependency overrides, config, middleware, deployment.
- **Done when:** Tests pass and the app runs in a container.

### Stage 8: Advanced (optional)
- **Build:** Pick any: WebSocket live updates, file attachments, rate limiting, custom exception handlers.
- **Done when:** The chosen feature works end to end.

## Out of scope

- A frontend UI
- Cloud deployment beyond a working Dockerfile
- Multi-tenant or team features

## How we work

- One stage at a time. We don't start the next until the current one is understood.
- After each stage: update `requirements.txt` and commit.
